## Ranked findings

**Blockers**

1. **`look.py` `set_down` (chain/`ok` semantics): `commanded_ok(..., ret_q=True)` returns `False`, not `None`, when IK passes but a check fails** — actually the reverse: `commanded_ok` returns `None` on *check* failure and `False` only… read it again: it returns `None if ret_q else False` on check fail, `q` on success, so `False` is unreachable with `ret_q`. **Real bug:** in `chain`, the condition `if ok is not None and ok is not False` accepts `ok = 0`-ish values fine, but `commanded_ok` with `q0=q` where `q` came from `ik(cur…, q0=zeros)` for `i<3` is inconsistent — for `i>=3` `q = cur.get("q")`, yet `here = (cur["ee"], cur["rpy"])` is used as poses[0] while `q0` belongs to that pose only if `cur["q"]` is the joint state at `cur`. "hold" calls store `q` of the *move* pose, so passing `q0=qc` with first pose `cur` is right only because both are the same waypoint — OK. The actual blocker: **`q0=np.zeros(6)` seed for `i<3`** (`q = ik(…)[0]` fallback) can pick a joint configuration on the *other elbow branch* from the one the arm physically is in after driving `i` calls; `commanded_ok` then rejects via the 0.5 rad jump check, `chain` returns `drop()`, and the parcel is **released mid-air over an arbitrary show point**, likely outside the delivery arm's reach → false reject or drop. Scenario: code confirmed on first face view, `done` small, "orig" route fails → drop. Fix: carry the true joint state (the harness knows it via `state`), pass it as `q0`, and on route failure fall back to *reversing the driven trail* before dropping.

2. **`state_machine.py` `SHOW` branch: confirmed code is taken from *any* camera, including the bin ROIs exclusion that only applies to the head.** `harness.py` builds `codes` (head, bins excluded) but `wrist` is *all* non-front images. A QR on a parcel already sitting in a bin, or a fixture/test label in the wrist field, decodes during SHOW, `self.pend` gets a *wrong* code, and the parcel is routed to the wrong lane. Failure: labelled parcel in black bin + valid code on another object in the wrist FOV → misroute. Fix: restrict wrist confirmations to the parcel (only accept codes whose head *or* bin check places them on the held parcel; simplest: confirm codes only by head for routing, wrist only for the faces in `self.show["faces"]` with text validated against `code_pattern` *and* seen in ≥2 views or with the parcel in hand).

3. **`harness.py` `scripted_reply` SHOWSET: `n = sp and len(sp["calls"])` then `if sp and i < n` — after SHOWSET calls finish, it returns `home_response` for `i < n + home_calls`; but `sm.calls` for SHOWSET is reset to 0 on entry while `plan_showset` computes the sset plan with `done = pre+1` where `pre = self.sm.calls` *before* `sm.step` — i.e. the *previous* state's call count, which is the last SHOW call index. `show_done = pre + 1` is off-by-one: `set_down` treats `done` as "calls driven" = index+1; `pre` was `sm.calls` at SHOW time = number of calls *completed* in SHOW = last driven index + 1 already, so `pre+1` skips one call. Net: set_down is planned from a pose one call *behind* where the arm actually is (it will re-command the tail of the driven trail — mostly harmless but can conflict with gripper state). Fix: `self.show_done = pre` (calls completed).

**Should-fix**

4. **`look.py` `show_plan` `views_at`: `held_low` uses `tip_of` (fingertips) but the parcel centre is `hold[2]/2 - grasp_depth` below the tip *along box x*; at non-90° pitch the tilt is `90−hold[3]` per `box_R`, yet `held_low`'s corner term `np.abs(R[2]) @ […]` mixes box axes (narrow, broad, height) — the order in `held_low`'s vector `[hold[2]/2, hold[0]/2, hold[1]/2]` assumes axes (x=height, y=narrow, z=broad) while `hold` is built as `(narrow, broad, height, pitch)` and `box_R` rotates about tool-y. For `hold[3]=π/2` it cancels; for 70–90° grasp pitches the clearance can be *under*-estimated → parcel scrapes the table mid-view. Fix: derive the held box corners explicitly in world frame and take min z; unit-test against the flat-on-table invariant for all grasp pitches (test only checks 90/70 for z-low equality — add 80/85).

5. **`grasp_plan` yaw set: `sorted((y0, (y0+2π)%(2π)−π), …)` — the second candidate equals `y0` after normalization (adding 2π then folding). The "either jaw sign" is lost; fingers close only in one sign. If that sign puts a jaw into the parcel (asymmetric fit) the plan is silently wrong. Fix: second candidate should be `y0 + π/2`-agnostic — the two jaw orientations are `y0` and `y0+π`… actually jaw axis sign gives `y0` vs `y0+π`; `(y0+π+π)` is a typo for `(y0+π)`. **This is a concrete bug** (file `grasp_plan`, `y0` line).

6. **`ik` rotation residual scale**: position residual is in metres, rotation residual `0.3*(R−Rt).ravel()` — for near-identity differences `||R−Rt||` ~ 2·angle; mixed-magnitude least squares under-weights orientation when position error is small, biased by seed. Consequence: `er < 0.05` acceptance (~2.9°) is looser than the 0.15 rad sampling in `commanded_ok`; views can be off-axis beyond `vis_min` margins in practice. Use SO(3) residual (log map) or a consistent scale; re-verify `vis_min` holds with measured orientation.

7. **`spin_plan` `inside()` uses the *pre-push* centre `c` for all legs including retract/up/home (legs 4–6)** — but the parcel has moved/rotated by the end; a tip that was outside pre-box can be *inside post-box* on the way home. `slide_plan` handles this (`k>4` uses `c_after`); `spin_plan` does not. Fix: predict post-push yaw (it knows `sigma` and torque sign) and check the last legs against the predicted footprint.

8. **`fit_parcel` `fill` denominator multiplies by `contourArea(tbl)`** — `tbl` is the *projected hull*; `contourArea(tbl)` can exceed `L0*L1` legitimately (hull ≠ rect, but tbl is the hull). Solidity×(hull/rect) is not a standard fill test; on perspective-skewed hulls `L0*L1` (minAreaRect area) ≈ hull area, so the second factor ≈1 and `fill` ≈ blob/hull — fine, but the `1e-9` guard suggests authors saw `L0*L1` underflow; use the `rect` area `cv2.minAreaRect` returns (`rect[2]*rect[3]`) instead. Minor correctness: also `minAreaRect` on the *projected* points uses the hull as a polygon in metres — correct, good.

9. **`views()` azimuth range 90–270° only (near half-circle) drops the far side.** For parcels delivered to the left with the right arm home, the near side is mostly blocked by the robot; the docstring admits "empty list is a valid answer" — but LOOK is disabled by default, so acceptable; note it for re-enable.

**Minor**

10. `pixel_to_table` uses `d[2]` with OpenGL −z; consistent with `table_to_pixel` — verified invertible. Good. But `footprint` projects corners at `TABLE_Z + target_h` while the blob includes the front face whose top edge is higher — hw overestimated; conservative, OK.
11. `test_v8` `cached_show_plan` monkeypatches `look.show_plan` module-globally across the test session — any test importing the real function later (e.g. `set_down` calling `grasp_plan` is fine, but `plan_show` uses patched) sees cached results keyed only on rounded c/half/yaw: two configs differing in `arm_y` (0.266 vs 0.29) share cache keys → **stale plans across cfg variants in the same pytest process**.
12. `home_response`/other arm: `scripted_reply` for SHOW sets the *other* arm to `self.home[other]` (root-frame dict?) — `self.home` is `state` (arm-frame positions). `move_response` expects arm-frame; `self.home` was captured from `state` so it is arm-frame — consistent, but `homes()` converts `state[arm]["position"]` (arm-frame) into root by adding `frame(arm)` — **double transform**: `homes()` treats `state` as root-frame. If `state` is arm-frame (as `to_arm`'s docstring "the WALLX state / targets (absolute, per-arm base)" says), `homes()` is wrong by the arm-base offset, feeding wrong `home` into every `commanded_ok` first pose. **This may be the real root of finding 1's branch jumps.** Fix: pick one convention; `homes()` should *not* add `frame` if `state` is arm-frame.

**(a) Is SHOW physically sound?** Grasp pitch: parcel is tilted `90°−pitch` in hand; only *flat* on the table at the grasp pitch, which `set_down` enforces — sound. Force via over-close: 0.3 gripper units ≈ 19 mm opening < 50 mm minimum side — sound, but confirm sim gripper torque; a 152 mm-tall kraft box held by fingertips 20 mm below the top has the CG offset — check tip loads. Held-parcel model: sound for 90° pitches, suspect for 70° (finding 4). Set-down landing flat: parcel drops `place_lift` 5 cm onto the handoff spot — 5 cm free fall of a box you're trying not to damage; it will rotate/tilt on impact, and `fit`/`grasp_plan(deliv)` assume it lands *flat at the planned yaw* — the post-landing orientation is unmodelled; the WALLX place then grasps a tilted box 30% of the time at best. Acceptable as fallback, high-risk on the critical path.

**(b) Missing side + bottom fastest:** cheapest is a **tipped re-show**: set the parcel down on an *edge* (narrow edge flat, 89/76 mm edge ≤ table clearance) so the two never-shown sides plus the bottom face the head at table level — one scripted set-down-rotated + a second short SHOWSET-style view, no second arm. Two-arm re-grasp is slower (grasp 30% ×2). Bottom-face QR on a tipped box is visible only to the *wrist* camera, which can do a scripted oblique approach like LOOK. Recommend: SHOW (4 sides) → tipped set-down + wrist oblique (bottom + far side) → SPIN only as last resort. Budget-wise this is ~8–10 calls vs SPIN's 4×12.

**(c) <1 min/parcel with cloud WALLX?** Per parcel, best cloud flow: SCAN ~3×11 s ≈ 33 s (head decode) + PLACE ~3×11 ≈ 33 s + home/verify ≈ 2×2.2 s ≈ **70 s** — over 60 s. With SHOW added (≈40 s scripted, no WALLX) you're at ~110 s *before* the wallx delivery. **The <1 min goal is not reachable with cloud WALLX while keeping 2 confirmed frames + 3 PLACE tries.** Fastest defensible: (1) drop `scan_max_calls` to 3, accept a single-frame head decode at 2× crop as *tentative* with confirmation folded into the first PLACE dwell (route on first confirmed decode, place in 1 try, verify in 1 call → SCAN 2 + PLACE 1 + HOME 1 + VERIFY 1 = 5 WALLX calls ≈ 55 s + scripted overhead); (2) make SHOW the primary search (0 WALLX calls) and stop at first valid decode; (3) set `wallx_call_s` budget to the observed local mean and run the **local Wall-OSS backend** for label-visible parcels (~1.2 s/call → full flow ≈ 15–20 s, comfortably under 1 min). Cloud-only is defensible only for the reject path where you can short-circuit to `deliver_reserve` and skip retries.

Priority order to fix before burning sim hours: 1, 12, 5, 3, 4, 2.
