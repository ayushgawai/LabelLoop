# Desktop robot client and WALLX at the event

Keep the desktop G-gripper on synchronous public_v2 for the current relay. At the task's ~1.4 s observation cycle and the runbook's 0.07 s LAN inference, even eliminating the entire model call would save only ~5% per cycle. The remaining ~1.33 s includes work outside inference. Its breakdown is unmeasured. A wrong-object grasp costs a whole attempt. [docs/tasks/CAPABILITIES.md:11–13; docs/EVENT_RUNBOOK.md:3–6; scripts/trial_agent.py:42–55]

## Client options and effective settings

The wrapper delegates to infer_session.py, whose parser is absent. [S:1–17,25–28]

| Option or field | Effect and default evidence |
|---|---|
| `--model-address`, `--instruction` | Select the downstream policy endpoint and goal text. Event task uses the Mac relay and “put the box into the blue bin”. The trial launcher supplies both explicitly. Bare CLI defaults unknown. [T:5–12,23–27; A:20–25] |
| `--robot-mode`, `--attach` | Event launcher selects `end_pose` and attaches to the stack. WebUI uses `robot_type: DESKTOP`, `mode_type: EndPose`. Wrapper ordinarily starts infer node + dispatcher and issues INIT/START. Attach lifecycle details and flag defaults unknown. [A:23–25; S:10–17,25–28; T:8–11] |
| `--infer-type sync\|async` | Sync waits for a prediction per request. Async implementations exist for desktop, including RTC. Event task selects sync and sets nested `algorithm: sync`. Bare infer-type default unknown. Changing only this flag cannot enable RTC through this relay. [C:55–60; T:11–19; E:21–29,163–180] |
| `--infer-params` | Wrapper default preset is `wallx_2606_ex001_g_rtc`. Override with a WebUI model config as inline JSON or `@file.json`. Event task explicitly supplies its own sync infer_params object. The default preset's contents and override merge rules are absent. [S:13–17; T:11–21] |
| `action_horizon` | Number of predicted action samples per chunk. Event config 32, matching the public example and our hold generator. Sharpa uses 30 and EX002 uses 40. Prediction length alone does not establish how many samples the dispatcher executes before refreshing. [T:12–16; W:18,179–184; R:12–22; C:153–168] |
| `control_dt`, `interpolate_multiplier` | Control tick period in seconds and subdivision of model steps into finer control steps. Both examples use 0.005 s, with multipliers 10 (Sharpa) and 5 (EX002). G values and exact dispatcher timing law unknown. Changing either can alter physical speed as well as smoothness. [C:104–106,146–168; L:12–15; T:12–20] |
| Camera resize, capture, history and JPEG quality | Desktop G resize, resolution, JPEG quality and CLI spellings unknown. Sharpa sets `camera_capture_hz: 20`, `camera_history_k: 1`. LabelLoop's encoder defaults to quality 80, but event JPEGs arrive encoded. Optional relay overlays re-encode only the front at 85. [C:146–156; W:211–224; E:69–83,151–155] |
| `--image-wire-format`, `api_schema` | Event launcher uses CLI `base64`, event task uses `image_wire_format: base64_jpeg`, `api_schema: public_v2`. Validator expects three nonempty strings. ### RTC presets and public protocol

| Setting | Meaning and scope |
|---|---|
| Sharpa training-time preset | Default instruction “unbox the fan.” Nested `async_params` select `algorithm: rtc`, `rtc_mode: training_time`, `execute_horizon: 20` samples, `num_flow_steps: 10` model integration steps and `max_inference_delay: 10`. The Sharpa launcher uses these values. The infer node uses them with override, otherwise WebUI supplies its own. [C:146–164] |
| EX002 JSON example | `algorithm: training_time_rtc`, `rtc_mode: training_time`, `execute_horizon: 20`, initial delay estimate 7, maximum 10, `rtc_cap_enable: false`, HIL interpolation multiplier bounds 1–20. The excerpt supplies values but does not define the cap or when HIL applies. Neither preset establishes legal public_v2 delay values for this event. [C:165–181; L:12–15; R:22–33] |
| First public RTC request | Send current observation and instruction, omitting all three RTC fields. The documented quanta leader–follower example predicts 32 frames, dispatches left and right indices 0–5 together at 33.7 ms/frame (~0.20 s) and retains the full prediction. Desktop G timing is unverified. [R:8–22] |
| Subsequent requests | Supply current images and state, `use_rtc: true`, integer `inference_delay` equal to frames still executing during inference (1–4, example 4), and `prev_action_chunk`. Delay 5 or 6 yields `rtc_delay_exceeds_training`. For each arm's position, RPY and gripper, take `previous[:1] + previous[6:]` as sequence concatenation, from the latest prediction. Keep ≥2 frames including frame 0, which the service discards. Dispatch the next six from index 0. Omit wire field `rtc_mode`. [R:22–37,51–76] |

### What the harness can send

- **Transport.** A persistent WebSocket exchanges binary MessagePack with NumPy support. Upstream sends metadata first, which the relay forwards. LAN uses the cloud public_v2 contract without auth. The relay limits inbound frames to 32 MiB. [W:29–36,61–77,155–168; E:17–18,126–137,202–203]
- **Request.** Top-level fields are `embodiment`, nonempty `instruction`, `observation`, optional `normalization` and `reset_history`, plus the conditional RTC fields above. `observation.images` carries Base64 JPEGs named `front`, `left_wrist`, `right_wrist`. Under `observation.state`, each of `left_ee` and `right_ee` has finite `position[3]`, `rotation_rpy[3]` and scalar `gripper`. Preserve the measured values and the hardware's frame and units. [E:21–42; W:171–176; docs/EVENT_RUNBOOK.md:74–77]
- **Reply.** Public actions repeat each arm's three state fields over time under `actions`, alongside `embodiment`. The relay forwards WALLX actions and structured errors. The native self-hosted backend instead sends `views`, `instruction` and home-relative `state.follow1_pos/follow2_pos`, strips the state echo from a 33-row reply and converts to public arm fields. That adapter's history behavior and row offset do not apply to LAN. [R:19–33,68–76; W:110–121,134–152; E:168–180]
- **Extra context.** The relay preserves incoming extra keys while replacing the instruction and optionally the front image. No supplied contract gives extra keys such as a ZIP, bounding box, confidence or target pose any model semantics. Put parcel location, acting arm and destination in the supported instruction. For visual prompts the relay supports `--overlay none|parcel|mask|grid`, default `none`. Perception sees the raw frame before the upstream overlay. [E:69–91,150–172,210–221; labelloop/perception/overlay.py:43–76; A:42–49]

## Ranked changes for the event relay

Desktop command for the sync comparison, using the installed script directory after the organizer session environment is loaded. It preserves the trial launcher's explicit flags. The current task's sync parameter object is shown separately so it can be pinned without relying on the wrapper's RTC preset. [A:23–25; S:13–17; T:8–21]

```sh
python3 /opt/xr/bot/x2robot_client/share/x2robot_client/scripts/start_desktop.py \
  --model-address 192.168.1.157:8001 --instruction 'put the box into the blue bin' \
  --robot-mode end_pose --infer-type sync --embodiment teletwin_desktop/gripper-g \
  --image-wire-format base64 --attach --home-on-stop \
  --infer-params '{"action_horizon":32,"async_params":{"algorithm":"sync","api_schema":"public_v2","embodiment":"teletwin_desktop/gripper-g","normalization":"provided","image_wire_format":"base64_jpeg"}}'
```

1. **Prevent the wrong grasp first.** Keep the client above and relay `--profile real --fast --overlay none`. For a wide, flat parcel, compare the default PLACE with a relay `--wording FILE` containing `{"PLACE":"Use both arms to lift the small flat package at the {where} of the green table by its short ends, then put it into the {mat} bin."}` For a parcel that fits, use “Use the {arm} arm to pick up the small flat package at the {where} of the green table, then put it into the {mat} bin.” Hold the start pose and parcel constant. Compare first-attempt lifts and correct releases. Raw images previously led to parcel contact, while the parcel overlay led to a bin lift. Neither establishes successful placement. [A:42–65; E:210–221,226–233; labelloop/harness.py:44–52]
2. **Measure the 1.33 s before changing timing.** In `Relay.handle_wallx`, timestamp consecutive downstream arrivals for the same goal using `time.monotonic()`. Log that interval alongside `elapsed_ms` (receive through send) and `latency_ms` (upstream infer only). Time decode/harness and recorder separately. The recorder runs after send and can delay the next read. If duplicate camera saves matter, add relay `--save-images ''` while retaining trial recording. Preserve the full front image for the ~60 px QR. Judge changes on median and slow-cycle times as well as read rate. [E:134–154,168–192,217–220; docs/AGENT_CONTEXT.md:29–35]
3. **Refresh sooner without speeding up physical playback.** Keep sync, control timing and the 32-frame upstream prediction. Proposed relay change for an offline dispatcher replay: return only `values[:N]` for every action channel of both arms on successful WALLX replies, starting with N=16 against the full 32. First verify that the G dispatcher accepts short replies and requests fresh observations rather than padding, rejecting or draining a fixed queue. Compare boundary jumps and whether closes/lifts finish across replans. Shorter chunks are a test hypothesis, with no established G execution-horizon flag. Keep the full reply if the contract requires 32. [T:9–20; E:168–180; R:12–22]
4. **Use RTC for continuity only after verifying dispatch support.** Proposed relay change: replace the blanket rejection in `validate_request` with conditional validation for the documented RTC triple (both arms, matching finite channel lengths and shapes, delay 1–4). Forward client-generated carry-over only for uninterrupted WALLX motion in the same goal. On HOLD, retry, goal change or reconnect, require a fresh first cycle and discarded queued actions at the dispatcher. Never reconstruct executed indices from relay time alone. Candidate client change is `--infer-type async` with an organizer-confirmed desktop G public_v2 RTC config replacing the sync JSON. The excerpts provide no such complete G config. Check synchronized dispatch and trajectory continuity in replay before hardware use. [E:21–42,138–169; R:8–37,54–76; C:55–60]
5. **Keep history within an attempt.** In `handle_wallx`, set `fresh = True` on each downstream goal change. Latch a pending reset across local HOLD and scripted replies and clear it only after the first successful upstream prediction for the new attempt. Preserve history for successive predictions toward the same target. This covers goal changes on one connection and retries whose transition occurred on a local reply. [E:126–146,155–180; W:171–176; labelloop/harness.py:193–195]

## Stop and abort boundaries

- The fastest documented emergency stop is the tested physical e-stop with a person beside it. Ctrl-C starts the client STOP/CLOSE sequence. The trial launcher also requests homing. Neither WebSocket close nor relay process exit has a documented guarantee of cancelling queued frames. The relay itself directs the operator to stop the session in WebUI on failure. [docs/EVENT_RUNBOOK.md:8–19; S:15–17; A:23–25; E:193–199,242–246]
- For a detected bad outcome, event_fast already latches HOLD on detected non-target bin motion. The next hold reply repeats measured state for 32 frames and skips inference. A missed/dropped grasp can end an attempt on a fresh observation if gripper checks are enabled and calibrated. A shorter verified dispatch prefix would bring that observation forward. A relay-only HOLD cannot preempt frames already on the robot. [labelloop/brain/state_machine.py:124–143,311–321; E:155–163; W:179–184]
- The runbook gates real-arm work on stationary checks and supervised one-parcel operation with retries and wrist reads off. The implementation of event_fast overrides several real-safe defaults, including retries and WALLX reject motions. Use `--profile real --real-safe --no-fast` for the runbook's initial mode and verify its scripted HOME behavior against the go/no-go list before arming. The ranked fast-mode comparisons are proposals. No network, robot or credentials were used in this review. [docs/EVENT_RUNBOOK.md:8–19,54–61; E:214–217,230–233; labelloop/harness.py:39–48,289–295]
